# Deploying MedGuardX

Two independent deployments, no containers:

- **API + database → Render** (native Python runtime + managed Postgres)
- **Web → Vercel** (native Next.js)

They are wired together by two settings: the web app's `NEXT_PUBLIC_API_URL`
points at the Render API, and the API's `MEDGUARDX_CORS_ORIGINS` allows the Vercel
origin.

---

## 1. API on Render

The repo ships [`render.yaml`](render.yaml) as a Blueprint. It provisions a free
Postgres instance and a Python web service built straight from source.

### Deploy

1. In Render → **New → Blueprint**, pick this repo. Render reads `render.yaml`.
2. Before the first deploy, set the one secret that can't be auto-generated:
   - **`MEDGUARDX_FERNET_KEY`** — a real Fernet key. Generate it locally:
     ```bash
     python -c "from cryptography.fernet import Fernet; print(Fernet.generate_key().decode())"
     ```
     Paste the value into the service's environment. **Never rotate it** — all
     records are encrypted with it and become unreadable if it changes.
3. Deploy. `MEDGUARDX_JWT_SECRET` is generated by Render, and
   `MEDGUARDX_DATABASE_URL` is injected from the Postgres instance automatically.

### What `render.yaml` configures

| Setting | Value | Why |
|---|---|---|
| `buildCommand` | `pip install './packages/medguardx-core' && python -m spacy download en_core_web_md && pip install './apps/api[postgres]'` | Installs the engine, downloads the `md` model, then the API, from the repo root |
| `startCommand` | `uvicorn medguardx_api.main:app --host 0.0.0.0 --port $PORT` | Native ASGI server |
| `healthCheckPath` | `/health` | Render waits for the app (and model) to be ready |
| `MEDGUARDX_ENVIRONMENT` | `production` | Enforces secrets + non-wildcard CORS at startup |
| `MEDGUARDX_MODEL` | `en_core_web_md` | Fits the free tier's RAM; swap for `lg`/`trf` on a bigger plan |
| `MEDGUARDX_CORS_ORIGINS` | your Vercel origin(s) | Update to match your web domain |

After deploy, note the service URL (e.g. `https://medguardx-backend.onrender.com`)
— the web app needs it.

### Caveats on Render's native runtime

- **Cold starts:** free services sleep when idle; the first request after sleep
  waits for boot **plus** the one-time spaCy model load. `/health` covers startup;
  end users just see a slow first hit.
- **Image OCR:** `pytesseract` needs the system `tesseract` binary, which the
  native runtime does not provide. **Text, PDF, and HL7 ingestion work fully**;
  image uploads will report an OCR-unavailable error. If you need OCR, run the API
  on a host where you can install `tesseract-ocr`.

## 2. Web on Vercel

The web app is `apps/web` — a standard Next.js 14 project, with
[`apps/web/vercel.json`](apps/web/vercel.json) pinning the framework and commands.

### Deploy

1. In Vercel → **New Project**, import this repo.
2. Set **Root Directory = `apps/web`** (this is the only monorepo-specific step;
   Vercel then reads `apps/web/vercel.json` and auto-detects Next.js).
3. Add an environment variable:
   - **`NEXT_PUBLIC_API_URL`** = your Render API URL, e.g.
     `https://medguardx-backend.onrender.com`
   (It is inlined at build time, so a change requires a redeploy.)
4. Deploy. Note the assigned domain, e.g. `https://med-guard-x.vercel.app`.

### Close the loop

Back in Render, set **`MEDGUARDX_CORS_ORIGINS`** to your Vercel domain
(comma-separated if you have several, e.g. a preview domain). No wildcards in
production — the service rejects `*` when `MEDGUARDX_ENVIRONMENT=production`.

## 3. Verify

```bash
API=https://medguardx-backend.onrender.com

curl "$API/health"                 # {"status":"ok"}
curl -o /dev/null -w "%{http_code}\n" "$API/api/stats"   # 401 -> auth is enforced
```

Then open the Vercel URL, register a user, and confirm upload/retrieve/preview work
end to end.

## Environment variable reference (API)

| Variable | Required in prod | Notes |
|---|---|---|
| `MEDGUARDX_ENVIRONMENT` | — | `production` enables strict checks |
| `MEDGUARDX_JWT_SECRET` | ✅ | Render auto-generates via `render.yaml` |
| `MEDGUARDX_FERNET_KEY` | ✅ | Set manually; never rotate |
| `MEDGUARDX_DATABASE_URL` | ✅ | Injected from Render Postgres; `postgres://` is auto-normalized to `postgresql+psycopg://` |
| `MEDGUARDX_MODEL` | — | `en_core_web_sm/md/lg/trf` |
| `MEDGUARDX_CORS_ORIGINS` | ✅ | Comma-separated allowlist; no `*` |

## 4. Publishing `medguardx-core` to PyPI

The OSS engine publishes via **PyPI Trusted Publishing** (OIDC) — no API token or
secret is stored. The workflow is [`.github/workflows/publish-pypi.yml`](.github/workflows/publish-pypi.yml).

### One-time setup

1. Create a PyPI account (https://pypi.org).
2. Add a **pending trusted publisher**: https://pypi.org/manage/account/publishing/
   - PyPI Project Name: `medguardx-core`
   - Owner: `adarshcod30`
   - Repository name: `MedGuardX`
   - Workflow name: `publish-pypi.yml`
   - Environment name: *(leave blank)*

### Publish a release

Create a GitHub Release (e.g. tag `v1.0.0`) — the workflow builds and publishes
automatically. Or trigger it manually from the Actions tab (`workflow_dispatch`).

### Manual alternative (local, needs your own PyPI token)

```bash
cd packages/medguardx-core
python -m build
python -m twine upload dist/*        # prompts for your PyPI API token
```

Bump `version` in `packages/medguardx-core/pyproject.toml` for every release —
PyPI does not allow re-uploading the same version.
